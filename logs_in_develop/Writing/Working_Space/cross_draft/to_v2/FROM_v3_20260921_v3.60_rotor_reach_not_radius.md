# From v3 → v2 · 2026-09-21 · v3.60

## `0.31`\,m is the quadrotor's **rotor reach**, not a vehicle radius — and it is not a tightening

Two separate offsets were being merged in v3's Chapter 5, and the same merge is likely in Chapter 4.
v3 has now split them. Chapter 4 keeps one wording that should follow.

### What the configuration actually has

| knob | value | where | what it is |
| :-- | :-- | :-- | :-- |
| `enlarge_constraints` | $0.025$\,m | `config/uav_projection.yaml:152` | the **tightening** margin, the value DPCC introduces; active **only** for `-tightened` variants; the same quantity in all three environments |
| `inflation.r_drone` | $0.31$\,m | `config/uav_projection.yaml:175` | **body inflation** — an always-on offset applied in `setup_dpcc_projector`, explicitly documented at `:160--174` as *distinct from* the tightened enlarge |
| `inflation.margin_base` | $0.02$\,m | same line | a planning pad on top of the body reach |

The config file says so in its own words at `:876`:

> 🔴 THE TIGHTENING KNOB IS NOT USED TO DO THIS. `enlarge_constraints` stays at 0.025 and keeps
> meaning what it means in every other table of the thesis; the enlargement lives in the entry's
> own `radius`, so the two stay distinguishable.

### Why "radius" is the wrong word

`r_drone = 0.31` is the **largest per-axis rotor reach at zero yaw**, not the radius of a
circumscribing disk. The four rotors sit at $(\pm 0.14, \pm 0.18)$\,m
(`d3il/environments/d3il/models/mj/robot/quadrotor/quadrotor_modified.xml:43--46`) and each rotor is
an ellipsoid of radius $0.13$ (`:17`), so:

- across the vehicle: $0.18 + 0.13 = 0.31$\,m
- along the vehicle:  $0.14 + 0.13 = 0.27$\,m

The larger is taken. The same constant is `uav_expert_data_collect/trajectories.py:44`
(`PILLAR_ROTOR_REACH = 0.31`), the number the demonstrated channels were laid out around. An earlier
value of $0.36$ (the worst-case *diagonal* tip radius) was withdrawn because the vehicle never yaws in
these scenes.

### The one line to change in v2

`chapters/04_method.tex:1505`:

> Walls and disks are inflated by the vehicle radius $r\sidx{b}$, so a plan for the vehicle's centre keeps …

Suggested: **the vehicle's rotor reach $r\sidx{b}$**. The sentence is otherwise right, and its point —
that the plan is for the centre — is exactly the framing v3 has adopted.

### One more thing worth knowing, for any Chapter 4 sentence about scoring

Planner and scorer do **not** use the same margin. The planner is offset by $0.31 + 0.02$
($+\,0.025$ when tightened); the execution-time scorer `_exec_constraint_violations`
(`mix_uav_test/eval_mix_uav.py:793--806`) uses $0.31$ **alone** — it checks the flown path against the
raw geometry $\oplus$ the rotor reach, deliberately not against the planning margin. v3 records this in
a `\srcnote` at `sec:setup:protocol:eval`.
