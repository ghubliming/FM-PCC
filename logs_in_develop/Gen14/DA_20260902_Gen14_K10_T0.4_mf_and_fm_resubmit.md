## 1.1 The fm job failed on the bug we already fixed — because it ran the pre-fix commit

```
File ".../mix_visual_aligning/sampling/hardflow_projection.py", line 938, in encode_visual_cond
AttributeError: 'VisualFlowMatching' object has no attribute '_encode_once'
```

Identical to job 25248. **This is not a regression and not a second bug.** Both logs stamp:

```
GIT REV:   7ae33be
```

`7ae33beb` is **two commits before `159a0318`**, which is where the Fix_11 `hasattr` branch landed. The cluster checkout was behind when `sbatch` fired.

The traceback is itself the proof. Python prints the source line by re-reading the file at the moment the exception is formatted, and what it printed for line 938 is *prose from the rewritten docstring*:

```
line 938, in encode_visual_cond
    Assuming `_encode_once` unconditionally raised `AttributeError: 'VisualFlowMatching'
```

That text does not exist in `7ae33be`. So the file **on disk** had the fix while the module **in memory** did not — the classic signature of a `git pull` landing after the process imported the module. The job was launched from the stale tree, the fix arrived mid-run, and the crash came from the old code object.

**Action: plain resubmit at current HEAD. No code change needed.** Verify `GIT REV` in the new log stamps `159a0318` or later before trusting the run.

## 2.1 The threshold moved down: it is now **2 < K\* ≤ 10**, not ≤ 20

The 09-01 DA could only bracket the collapse as `2 < K* ≤ 20`. K=10 closes half of that gap:

- **K=2 pushes the box *further from the target* on 4/10 contexts**, worst case 0.9030 m from a 0.4741 m start — it roughly doubles the error.
- **K=10 does that on 0/10.** Max 0.4387 m, i.e. it never makes a context worse than leaving the box alone.

So whatever fails at K=2 is **already fully repaired by K=10**. The failure is a threshold, not a gradual loss of resolution — h-coverage would predict smooth saturation and that is not what the data shows.

## 2.2 K=10 → K=20 is a real but unproven improvement; K=20 → K=100 is nothing

K=10 vs K=20 splits **5/5** and the permutation test gives **p = 0.250**. The +0.0797 m mean gap is not noise (the measured noise floor from the two identical K=100 unguided cells is **0.0079 m**, so this is ~10× noise) but it is carried by a few contexts and n=10 cannot resolve it. Read it as *directional, unproven*.

By contrast K=20 → K=100 costs **4.8×** and the mean moves the *wrong way* by 0.043–0.051 m, ns in both directions. **K=100 buys nothing on this task.**

## 3.2 Why the gap opened: the two projectors respond to earlier τ in *opposite directions*

Both runs make **exactly 4 projector calls per replan**. Only the τ window differs:

| run | τ of the 4 calls |
|---|---|
| K=20, T=0.2 | 0.80, 0.85, 0.90, 0.95 |
| K=10, T=0.4 | 0.60, 0.70, 0.80, 0.90 |

Moving to K=10/T=0.4 at fixed call count:

| arm | Δ ms (K10 − K20) | sign | p |
|---|---|---|---|
| **DPCC** | **+186.95** (got *more expensive*) | 23/4 | **< 0.001** |
| **HardFlow-SLSQP** | **−80.09** (got *cheaper*) | 0/27 | **< 0.001** |

That divergence is the mechanism. **HardFlow's cost tracks the sampler**, so halving NFE halves the part of its budget that scales — it behaves the way the cost model says it should. **DPCC's cost tracks solver difficulty**, and at earlier τ the iterate it is handed is further from the constraint manifold, so it burns far more solver iterations per call. Same four calls, +187 ms.

The practical reading: **lowering K is cheap for HardFlow and expensive for DPCC.** If the operating point moves toward low NFE, the in-loop projector is the one that survives the move.

# Part 4 — What this settles and what it does not

**Settled:**

1. **K\* is bounded above by 10, not 20.** K=10 removes every worse-than-nothing outcome that K=2 produced. The remaining bracket is `2 < K* ≤ 10`.
2. **K=10 → K=20 is directional only** (5/5, p=0.250, gap ~10× noise floor). K=20 remains the safe operating point for quality; K=10 is the operating point if latency matters.
3. **K=20 → K=100 buys nothing at 4.8× the cost**, confirmed a second time.
4. **The sampler is exactly linear in NFE**: `ms = 8.43 + 9.159·K`, max residual 1.7 ms across K = 2…100.
5. **HardFlow-SLSQP beats the DPCC projector at K=10 on latency with real significance** (2.4×, p ≤ 0.0039 per variant) while being strictly better on constraints — the first significant arm-B/arm-C result in this corpus. Per the benchmark hierarchy this is the HardFlow-must-beat-the-DPCC-projector requirement, met at a *lower* projection threshold as specified.
6. **The two projectors scale oppositely in τ.** Lowering K helps HardFlow and hurts DPCC.

**Not settled:**

1. **The fm arm still has no arm-C data.** 25274 ran stale code; nothing about Fix_11 has been validated on the cluster yet.
2. **All of this is seed 6 only, n=10 contexts, one checkpoint.** The K=10 vs K=20 quality question needs more seeds, not more analysis.
3. **⚠ 100 % of arm-C items hit a non-converged SLSQP solve** (§1.3), at the second projector call, in both K configs. Executed violations are still 0.00, so the outcome is fine, but the terminal-solve feasibility *guarantee* does not hold as documented. Unquantified — only first failures are logged.
4. **No K between 2 and 10 exists.** If the threshold's location matters for the paper, K=5 is the single most informative missing cell.
5. **Untouched-box rates are high under `-t`/`-c` projection** (up to 6/10) and are not yet explained.

# Part 5 — Conclusion: is K=10 worth it?

**Short answer: yes for `hardflow_sls-r`, no for everything else. It is an
arm-conditional operating point, not a replacement for K=20.**

This is a different kind of result from K=100 → K=20, and the difference matters
for how it gets reported.

| retirement | why it was unconditional / conditional |
|---|---|
| **K=100 → K=20** | K=100 is worse-or-equal on **every** axis at **4.8×** the cost, twice confirmed (§2.2). Nothing is given up. **Retire K=100.** |
| **K=20 → K=10** | Depends on the arm. Dominant under HardFlow-`r`, degrading under DPCC, directionally worse unguided. **Keep both.** |

  baseline per the benchmark hierarchy, and it is missing.
- **`diffusion` can never have an arm C at all.** `resolve_engine_hf`
  (`hardflow_projection.py:899-914`) refuses it by design — a DDPM reverse chain
  has no velocity field, so `hardflow_new` is undefined on it. A diffusion run
  supplies **arms A and B only**. The cross-engine arm-C comparison is therefore
  `mf` vs `fm` vs `af`, and diffusion enters only as the arm-A/arm-B baseline.

So: **best horse in the stable so far**, not best horse full stop.

## 5.2 The compute budget: NFE **and** NLP solves

The user-facing question — *the thresholds differ too, so is the budget the
same?* — has to be answered on **two** meters, not one. Arm C spends network
evaluations *and* nonlinear solves, and they are matched differently.

### 5.2.1 ⚠ Correction: arm-C NFE is **not** K

`hardflow_projection.py:1188-1193` computes an extra velocity field at every
**genuine** step, to extrapolate the endpoint the NLP is actually solved on:

```python
if k < K - 1:
    V_next = self._velocity_batch(X_ref, tau_next, ...)   # +1 NFE
    X1_ref = X_ref + (1.0 - tau_next) * V_next
else:
    X1_ref = X_ref                                        # terminal: tau_next == 1, skipped
```

The terminal step skips it (the `1 − τ_next` weight is zero), so the code's own
accounting is **`policy.nfe = K + n_active − 1`**. Arms A and B have no
lookahead and stay at K.

| arm | NFE/replan @ K=10 | NFE/replan @ K=20 |
|---|---|---|
| A `diffuser` (unguided) | 10 | 20 |
| `post_processing` | 10 | 20 |
| B `dpcc-*` | 10 | 20 |
| **C `hardflow_sls-*`** | **13** (+30 %) | **23** (+15 %) |

Two consequences that were wrong or missing in the earlier framing:

1. **The K comparison in arm C is 13 vs 23 NFE — a 1.77× ratio, not 2×.** Every
   "half the NFE" phrasing in this DA is loose for arm C; it is 43 % less.
2. **Arms B and C are *not* NFE-matched at the same K.** Arm C spends 3 more
   network evals per replan. So §3.1's latency win is achieved **while spending
   more NFE, not less** — that strengthens the result rather than qualifying it.
3. The lookahead surcharge is regressive in K: **3/13 = 23 % of the arm-C budget
   at K=10 versus 3/23 = 13 % at K=20.** Low K makes the guidance overhead a
   larger share of the total.

### 5.2.2 NLP solves are matched by count, not by work

**The NLP solve count is identical across all four cells — both arms, both K.**
Verified from source, not assumed:

- **Same gate.** Arm B's projection trigger (`mf_diffusion.py:283-284`,
  `loop_idx >= int((1−T)·K) or loop_idx == K−1`) is the *same formula* as arm C's
  (`hardflow_projection.py:1169`). Both give `n_active = 4` at K=10/T=0.4 and at
  K=20/T=0.2.
- **Same candidate fan.** `eval_mix_visual_aligning.py:3302-3313` hands both
  `dpcc-*` and `hardflow_sls-*` the run-level `mpc_batch_size`, with the comment
  *"HardFlow is a projected arm and takes the same pool, so arms B and C are
  compared at equal candidate count."*
- **Same per-call solve count.** DPCC loops candidates *inside*
  `Projector.project` (`projection.py:236`, one scipy `minimize` per row); HardFlow
  loops candidates *outside* and calls the same `Projector` with a batch of one
  (`hardflow_projection.py:1197-1203`, `_build_slsqp_projector`). Either way it is
  one `minimize` per candidate per call.

⇒ **NLP solves per replan = `n_active` × B = 4B, for arm B and arm C, at K=10 and
at K=20.** Four cells, one number. The fan `B` was not extracted from these logs,
so no *absolute* per-solve millisecond figure is claimed — but B cancels in every
ratio below, both across K and across arms.

**And the solver is the same solver.** HardFlow does not ship its own NLP: it
imports DPCC's `Projector` (`_build_slsqp_projector`) and inherits its scipy
SLSQP settings verbatim — `maxiter=1000`, `tol=1e-6`, `Bounds(±5)`, and the same
problem dimension (`horizon × transition_dim`). **The one and only difference
between an arm-B solve and an arm-C solve is the point handed to it** (§5.4).

| meter | K=10 / T=0.4 | K=20 / T=0.2 | matched? |
|---|---|---|---|
| **sampler NFE** | **10** | **20** | ❌ **2×** — the axis under test |
| **lookahead NFE** (`n_active − 1`) | 3 | 3 | ✅ exact |
| **total arm-C NFE** | **13** | **23** | ❌ **1.77×** |
| **NLP solves/replan** (`n_active` × fan) | 4 × B | 4 × B | ✅ exact — **and identical to arm B's** |
| genuine HardFlow steps (`n_genuine`) | 3 | 3 | ✅ exact — both tier `HF_OK` |
| τ window of the 4 solves | 0.60, 0.70, 0.80, 0.90 | 0.80, 0.85, 0.90, 0.95 | ❌ **moved earlier** |
| `first_lookahead` (1 − τ_next at first genuine step) | **0.30** | **0.15** | ❌ **2×** |
| **work per NLP solve** | — | — | ❌ **the real variable — see §5.4** |
| non-converged solves | ≥ 6 logged (100 % of items) | ≥ 6 logged (100 % of items) | ✅ same rate, both unquantified (§1.3) |

So T is **not** a second NFE difference — it is the knob that holds the *solve
count* fixed while sampler NFE halves. What it cannot hold fixed is **where**
those solves land, and that is what changes their cost.

Incidentally, K=10 / T=0.4 sits closer to HardFlow's own reference operating
point (the paper's N=10 / A=0.5 → 4 genuine steps at `first_lookahead` 0.40)
than the K=20 flagship does. That is an argument for K=10 being the more
faithful configuration, not merely the cheaper one.

## 5.3 ⚠ The confound is structural — it cannot be tuned away

`n_active = max(K − int((1−A)·K), 1)` couples the two knobs. At K=10 there is no
T that reproduces K=20's late window at 4 calls:

| config | `n_active` / `n_genuine` | regime | usable? |
|---|---|---|---|
| K=10, T=0.4 | 4 / 3 | `HF_OK` | ✅ what was run |
| K=10, T=0.2 (matches K=20's *threshold*) | **2 / 1** | **`THIN`** | ❌ one nudge — unattributable by the code's own definition |
| K=20, T=0.4 (matches K=10's *window start*) | **8 / 7** | `HF_OK` | ❌ doubles the calls — changes a different variable |

**You can hold the call count fixed or the τ window fixed, never both.** Every
K comparison in arms B/C is therefore a two-variable move by construction. Only
**arm A is a clean NFE axis** (T inert), and there K=10 loses directionally.

This is why the K=10 arm-C result cannot be promoted to "K=10 is better": what
§3.3 actually shows is that *the K=10/T=0.4 configuration* dominates *the
K=20/T=0.2 configuration* for `-r`. Attributing that to NFE alone is unsupported.

## 5.4 The cost decomposition — and why the two projectors diverge

Subtracting the unguided cell (89.7 ms at K=10, 172.5 ms at K=20, tightened geo)
from each arm isolates the projector overhead:

| variant | overhead K=10 | overhead K=20 | per call K=10 | per call K=20 | **ratio** |
|---|---|---|---|---|---|
| `post_processing` (1 call) | 22.7 | 21.1 | 22.7 | 21.1 | 1.08 |
| **`hardflow_sls-r`** | **102.8** | **102.8** | 25.7 | 25.7 | **1.00** |
| `hardflow_sls-c` | 114.5 | 109.8 | 28.6 | 27.5 | 1.04 |
| `hardflow_sls-t` | 132.4 | 129.0 | 33.1 | 32.2 | 1.03 |
| `dpcc-r` | 427.8 | 93.4 | **107.0** | 23.3 | **4.58** |
| `dpcc-c` | 434.6 | 152.8 | 108.6 | 38.2 | 2.84 |
| `dpcc-t` | 343.8 | 150.7 | 86.0 | 37.7 | 2.28 |

**HardFlow's projector overhead is invariant to the τ window** — 102.8 ms for
`-r` in *both* configs, to the last digit, and within 4 % for `-c`/`-t`. **DPCC's
inflates 2.3–4.6×** when the same four calls move earlier. This is §3.2's
mechanism made quantitative, and it sharpens the claim: it is not that HardFlow
"got cheaper at K=10" — HardFlow's cost simply *did not change*, and the entire
−82.8 ms saving is sampler saving. DPCC, by contrast, pays for the earlier
window out of solver iterations.

Consequence: **the whole K=10 latency win is the sampler's, and any arm whose
projector cost is τ-invariant inherits it in full.** Arms whose cost tracks
solver difficulty do not.

### 5.4.1 Splitting the overhead into lookahead NFE vs. NLP work

The overhead column above still mixes two things for arm C: the 3 extra
velocity evals (§5.2.1) and the NLP solves. Pricing the lookahead at the
tightened-geo sampler slope (`ms ≈ 6.90 + 8.28·NFE`, a two-point fit — treat as
approximate) gives 3 × 8.28 ≈ **24.8 ms**, the same in both configs. Subtracting
it isolates the solver:

| variant | NLP-only K=10 | NLP-only K=20 | **per solve** K=10 | **per solve** K=20 |
|---|---|---|---|---|
| `hardflow_sls-r` | 78.0 | 78.0 | **19.5** | **19.5** |
| `hardflow_sls-c` | 89.7 | 85.0 | 22.4 | 21.2 |
| `hardflow_sls-t` | 107.6 | 104.2 | 26.9 | 26.0 |
| `dpcc-r` | 427.8 | 93.4 | **107.0** | 23.3 |
| `dpcc-c` | 434.6 | 152.8 | 108.6 | 38.2 |
| `dpcc-t` | 343.8 | 150.7 | 86.0 | 37.7 |

DPCC's cost **per solve**, against HardFlow's on the same variant:

| variant | late window (K=20) | early window (K=10) |
|---|---|---|
| `-r` | 1.20× | **5.49×** |
| `-c` | 1.80× | 4.85× |
| `-t` | 1.45× | 3.20× |

**At the late window the two projectors' solves cost roughly the same. At the
early window DPCC's explode and HardFlow's do not move at all.** That is the
finding, and the code says why: HardFlow never hands the solver the raw iterate.
It solves on `X1_ref = X_ref + (1 − τ_next)·V_next` — an *endpoint estimate* —
so the solver's starting point is near the data manifold at every τ, and its
difficulty is τ-invariant **by construction**. DPCC projects the iterate itself,
which at τ = 0.60 is far from the constraint manifold, so the same four solves
burn 4.6× the iterations.

This is the mechanical reason the two arms scale oppositely, and it also says
the effect is **not** a tuning artefact: it follows from where each method places
its projection, so it should reproduce at any K.

### 5.4.2 The budget closes exactly

With solve count held at 4B everywhere, the whole cost table reduces to two
terms — sampler NFE and work-per-solve — and they add up:

| arm | Δms (K=10 − K=20) | = sampler Δ | + NLP Δ |
|---|---|---|---|
| A `diffuser` | **−82.8** | −82.8 (10 fewer NFE) | — |
| **C `hardflow_sls-r`** | **−82.8** | −82.8 (10 fewer NFE) | **0.0** |
| B `dpcc-r` | **+251.6** | −82.8 | **+334.4** |

**Arm C's K-delta equals arm A's to the last digit (−82.8 ms both).** That is
the proof, independent of any fitted slope: HardFlow's four solves cost *exactly
the same* at τ ∈ {0.60…0.90} as at τ ∈ {0.80…0.95}. DPCC's four solves — same
count, same solver, same problem — cost **+334.4 ms** more in the earlier window,
which is what turns a −82.8 ms sampler saving into a +251.6 ms net loss.

Same solves. Same solver. Opposite outcome. The only free variable is the
warm start.

⚠️ Not in this accounting: the **non-converged solves** (§1.3). Six are logged per
run — first-failure-only, so the true count is unknown — and a non-converged
SLSQP runs to `maxiter`, making it the most expensive solve there is. Both
configs hit them at the *second* projector call. Until `nlp_failures` totals are
extracted, an unknown share of every per-solve figure above is maxed-out
non-convergence rather than real work.

## 5.5 The time-steps trade-off, priced

What each extra 10 NFE actually buys, per replan (~400 replans/rollout):

| arm | K=10 | K=20 | extra cost of K=20 | distance bought | verdict |
|---|---|---|---|---|---|
| unguided (all geos, §2) | 0.1730 m @ 99.2 ms | 0.0933 m @ 190.5 ms | **+91.3 ms** (1.92×) | **−0.0797 m (−46 %)** | a real purchase, if unproven |
| unguided (tightened geo) | 0.1992 m @ 89.7 ms | 0.1431 m @ 172.5 ms | +82.8 ms (1.92×) | −0.0561 m | same picture |
| **`hardflow_sls-r`** | 0.2365 m @ 192.5 ms | 0.2108 m @ 275.3 ms | **+82.8 ms** (1.43×) | **−0.0257 m, ns (p=0.289)** | **a bad purchase** |

**The trade-off inverts once the projector is in the loop.** Unguided, doubling
NFE cuts the distance error by 46 %. Under `hardflow_sls-r` the same doubling
recovers 0.0257 m — less than half the unguided gap — and does not clear
significance. The projector absorbs most of the sampler's accuracy deficit, so
the K=20 quality premium is largely paid for twice.

Supporting observation, offered as a hypothesis rather than a finding: the
*distance cost of projection* is **larger at K=20** (+0.0677 m vs unguided) than
at K=10 (+0.0373 m). The better the unguided plan, the further the projector has
to move it to satisfy the constraints — so a better sampler partly cancels its
own advantage under safety filtering. One seed, n=10; not established.

In wall-clock: `hardflow_sls-r` at K=10 saves **33 s per rollout** (82.8 ms ×
~400 replans), ~30 % of the arm's total, for no measurable constraint or
distance cost.

## 5.6 Conclusion

### 5.6.1 The answer

**Ride `hardflow_sls-r` at K=10 / T=0.4.** Perfect constraints, the cheapest
projected cell in the corpus, an honest distance number, and the closest
configuration to HardFlow's own reference operating point. Keep
`hardflow_sls-r` at K=20 / T=0.2 as the conservative alternate — it is the only
cell that beats it on anything (0.2108 m vs 0.2365 m, ns).

**Never ride DPCC at K=10.** Same solve count, same solver, 2.7× the cost and
worse constraints.

### 5.6.2 Why the two arms part company

Everything in Part 5 collapses to one sentence, and it is a *mechanism*, not a
correlation:

> HardFlow and DPCC run the **identical** scipy SLSQP, on the **identical**
> feasible set, the **identical** number of times (4 × B per replan). DPCC hands
> the solver the raw iterate at τ; HardFlow hands it
> `X1_ref = X_ref + (1 − τ_next)·V_next`, an endpoint estimate that sits near the
> data manifold at **every** τ. So HardFlow's solve difficulty is τ-invariant by
> construction and DPCC's is not.

Measured: HardFlow's four solves cost the same at both τ windows to the last
digit (§5.4.2). DPCC's cost **+334.4 ms** more in the earlier window. Because it
is structural — a consequence of *where* each method projects — it should
reproduce at any K, on any engine, in any task. That makes it the most portable
finding in this DA, and the one most worth carrying into the write-up.

Corollary worth stating plainly: **arm C wins on latency while spending *more*
network evaluations than arm B** (13 vs 10 NFE at K=10). It is not buying speed
with compute; it is buying it with a better warm start.

### 5.6.3 Status of each question

| question | status |
|---|---|
| Best cell overall? | ✅ **`hardflow_sls-r` @ K=10/T=0.4** — within `mf` only (§5.1.2). |
| Does K=10 replace K=20 the way K=20 replaced K=100? | ❌ **No.** K=100's retirement was unconditional (worse everywhere, 4.8× cost). K=10 is arm-conditional. **Keep both.** |
| Is the K=10 → K=20 *quality* gap resolved? | ❌ **No.** 5/5, p=0.250, ~10× noise floor. Needs seeds, not analysis. |
| Are the NLP solves matched? | ✅ **Exactly** — 4 × B for arm B and arm C, at both K. Verified from the gate, the fan, and the solve loop. |
| Is the NLP *work* matched? | ❌ **No, and that is the whole story.** HardFlow flat across τ; DPCC 4.6× worse at the early window. |
| Is the NFE matched? | ❌ Sampler 10 vs 20; **total arm-C 13 vs 23** (lookahead adds `n_active − 1`). Arm C also carries +3 NFE over arm B at equal K. |
| Is the arm-C K win attributable to NFE alone? | ✅ **Yes, for HardFlow** — its NLP delta is 0.0 ms, so the entire −82.8 ms is the 10 dropped sampler evals (§5.4.2). ❌ Not for DPCC, and not as a general statement about K, because the τ window moves with it (§5.3). |

### 5.6.4 How to report it

Headline the **mechanism**, not the operating point — it is the part that
generalises:

> *At a matched projection budget (4 solves/replan, same solver, same feasible
> set), HardFlow's solve cost is invariant to the activation window while DPCC's
> grows 4.6× as the window moves earlier. Lowering the sampler budget is
> therefore free for HardFlow and expensive for DPCC: at K=10 the HardFlow arm
> keeps a 1.000 zero-violation rate at 30 % lower cost than at K=20, while the
> DPCC arm loses on every axis.*

**Do not** write "K=10 is as good as K=20" — that is only true for `-r`, only
under HardFlow, only at n=10 on one seed.

### 5.6.5 What would change this verdict

Ordered by how much they would move it:

1. **The `fm` resubmit.** Per the benchmark hierarchy, `mf` has to beat naive
   flow matching, not just DPCC. Right now there is no `fm` arm-C data at all.
2. **A `diffusion` run at K=10 and K=20.** That is *the* baseline. Note it can
   supply **arms A and B only** — `resolve_engine_hf` refuses diffusion, so the
   diffusion row will never have an arm C (§5.1.2). Plan the table around that.
3. **Seeds.** Every Pareto claim here is n=10 at seed 6, with near-saturated
   constraint axes (many exact ties). Only seeds move them.
4. **The non-converged solves** (§1.3). 100 % of arm-C items, at the second
   projector call, in both configs. Until `nlp_failures` totals are extracted, an
   unknown share of the per-solve costs above is maxed-out non-convergence rather
   than real work — and the terminal-solve feasibility *guarantee* does not hold
   as documented.
