## Why U3 is needed

E5 U2 GIFs are **state-injection replays** — the drone is placed at stored positions via
`mj_forward` (kinematics only, no physics forces). This is correct for visualising the
trajectory, but it hides the actual physics interaction:

- Contact forces, rotor-pillar clips, wall bounces → invisible in state-injection GIF
- The drone appears to "fly through" obstacles because collision resolution is not run
- Attitude (quaternion) is injected from stored `q`, not computed live by physics

E5 U3 adds a **second GIF type** alongside the current state-injection GIF: a **physics
replay GIF** generated by re-running the exact original physics simulation and recording
frames from the live `mj_step` loop.

**Key enabler**: The `episode_id` encodes the original `trial_seed` in its 7-digit suffix.
`collect.py` line 90 uses `trial_seed = args.seed + i` and the filename suffix is
`{trial_seed:07d}`. So `pillars_L_L_L_pid_default_0000056` was generated with
`trial_seed=56`. Re-running `run_trial(scene, homotopy, controller, seed=56)` reproduces
the exact same trajectory, physics, and contact events.

---

## What U3 produces

Two GIF files per episode:

| GIF type | Folder | Generator | Physics | Use |
|---|---|---|---|---|
| State injection (E5 U2) | `gifs/{scene}/{homotopy}/` | `generate_trajectory_gifs.py` | `mj_forward` | Trajectory shape, position accuracy |
| Physics replay (U3 new) | `gifs_physics/{scene}/{homotopy}/` | `generate_physics_gifs.py` (new) | `mj_step` | Real contact dynamics, attitude, forces |

The physics GIF is the **digital twin** representation — it shows what the drone actually
experienced: contact force bounces, rotor clips visible as brief deflections, real
quaternion attitude from live physics (no stored q needed).

## Change A — New script: `generate_physics_gifs.py`

**File**: `uav_expert_data_collect/generate_physics_gifs.py` (new)

The script re-runs `run_trial` from the original seed to reproduce the physics, then
captures frames at the dataset frequency with visual overlays.

### Core loop

```python
from uav_expert_data_collect.generator import run_trial, SCENE_XMLS
import mujoco

def generate_physics_gif(episode_path, out_dir, frame_stride=3):
    ep = pickle.load(open(episode_path, 'rb'))

    # Recover trial_seed from episode_id: last 7 digits
    trial_seed = int(ep['episode_id'].split('_')[-1])

    # Re-run exact original physics — same seed, same homotopy, same gains
    # We cannot call run_trial because it returns AFTER the full rollout.
    # Instead, replicate the inner loop to capture frames mid-run.

    scene      = ep['scene']
    homotopy   = ep['homotopy']
    controller = ep['controller']

    model = mujoco.MjModel.from_xml_path(SCENE_XMLS[scene])
    data  = mujoco.MjData(model)
    renderer = mujoco.Renderer(model, height=480, width=640)

    # Re-initialise exactly as run_trial does
    rng = np.random.default_rng(trial_seed)
    traj_fn, init_pos, dur = _build_traj_and_init(scene, homotopy, rng)
    data.qpos[:3]  = init_pos
    data.qpos[3:7] = [1.0, 0.0, 0.0, 0.0]
    data.qvel[:]   = 0.0
    mujoco.mj_forward(model, data)

    pid = _make_pid(model, controller)
    dt  = float(model.opt.timestep)
    n_step = int(round(dur / dt))

    frames_bp, frames_track = [], []
    DATASET_STRIDE = max(1, round(1.0 / (dt * 33)))   # 33 Hz

    for k in range(n_step):
        t = k * dt
        p_des, v_des, a_des, yaw_des = traj_fn(t)
        p  = data.qpos[:3].copy()
        v  = data.qvel[:3].copy()
        q  = data.qpos[3:7].copy()
        om = data.qvel[3:6].copy()

        u = pid.compute(p, q, v, om, p_des, v_des, a_des, yaw_des)
        data.ctrl[:4] = u
        mujoco.mj_step(model, data)   # ← REAL PHYSICS, not mj_forward

        # Contact detection
        in_contact = any(
            model.geom(data.contact[ci].geom1).name != 'floor' and
            model.geom(data.contact[ci].geom2).name != 'floor'
            for ci in range(data.ncon)
        )

        if k % (DATASET_STRIDE * frame_stride) == 0:
            frame_bp    = _render_frame(renderer, model, data, 'bp',    in_contact, t, ep)
            frame_track = _render_frame(renderer, model, data, 'track', in_contact, t, ep)
            frames_bp.append(frame_bp)
            frames_track.append(frame_track)

    # Stitch bp + track side by side (same as E5 U2 GIFs)
    combined = [np.concatenate([f_bp, f_tr], axis=1)
                for f_bp, f_tr in zip(frames_bp, frames_track)]
    os.makedirs(out_dir, exist_ok=True)
    gif_path = os.path.join(out_dir, f"{ep['episode_id']}_physics.gif")
    imageio.mimsave(gif_path, combined, fps=33 / frame_stride)
    # E5 Fix2 pattern — renderer.close() raises AttributeError on some MuJoCo builds
    if hasattr(renderer, 'close'):
        renderer.close()
```

### Contact overlay in `_render_frame`

When `in_contact=True`, add a red border to the frame and a `CONTACT` text overlay:

```python
def _render_frame(renderer, model, data, cam_name, in_contact, t, ep):
    renderer.update_scene(data, camera=cam_name)
    frame = renderer.render().copy()

    # Base text overlay (same as E5 U2)
    cv2.putText(frame, f"{ep['scene']} | {ep['homotopy']} | T={t:.2f}s",
                (10, 20), cv2.FONT_HERSHEY_SIMPLEX, 0.5, (255,255,255), 1)

    if in_contact:
        # Red border 4px wide — visible at a glance
        frame[:4, :] = [0, 0, 255]
        frame[-4:, :] = [0, 0, 255]
        frame[:, :4] = [0, 0, 255]
        frame[:, -4:] = [0, 0, 255]
        cv2.putText(frame, 'CONTACT', (10, 45),
                    cv2.FONT_HERSHEY_SIMPLEX, 0.6, (0, 0, 255), 2)

    # Nearest obstacle distance bar (bottom strip)
    dist = _nearest_obstacle_dist(model, data, ep['obstacles'])
    bar_w = int(min(1.0, dist / 0.5) * frame.shape[1])   # 0→0.5m maps to 0→full width
    color = (0,255,0) if dist > 0.3 else (0,165,255) if dist > 0.15 else (0,0,255)
    frame[-8:-4, :bar_w] = color
    cv2.putText(frame, f'd={dist:.2f}m', (frame.shape[1]-80, frame.shape[0]-10),
                cv2.FONT_HERSHEY_SIMPLEX, 0.4, (255,255,255), 1)

    return frame
```

**Contact overlays**:
- Red border: contact is happening THIS frame (visual alarm)
- Proximity bar: obstacle distance gradient (green→orange→red) across bottom edge
- Distance text: `d=0.08m` in bottom-right corner

## Change B — SBATCH script: `generate_physics_gifs.sh`

**File**: `Slurm_Codes/sbatch/uav_expert_data/generate_physics_gifs.sh` (new)

Mirrors `generate_gifs.sh` but calls `generate_physics_gifs.py`. Same `$1`=max_episodes,
`$2`=scene, `$3`=mp4, `$4`=frame_stride arguments. Output to `gifs_physics/`.

**EGL note:** Unlike `collect.sh` (physics-only, `MUJOCO_GL=disabled`), this script creates
`mujoco.Renderer` → EGL IS used. Must have `MUJOCO_GL=egl` + `PYOPENGL_PLATFORM=egl` +
the 3-line GPU pinning block — same as `generate_gifs.sh` (Group B in SLURM IT CHANGELOG).
Do NOT use `MUJOCO_GL=disabled` here; `Renderer()` will crash.

```bash
export MUJOCO_GL="egl"
export PYOPENGL_PLATFORM="egl"
export MPLBACKEND="agg"
export CUDA_DEVICE_ORDER="PCI_BUS_ID"
ALLOCATED_GPU="${CUDA_VISIBLE_DEVICES%%,*}"
export MUJOCO_EGL_DEVICE_ID="$ALLOCATED_GPU"

python uav_expert_data_collect/generate_physics_gifs.py \
    --out-dir logs/uav_expert_data/gifs_physics \
    --max-episodes ${1:-""} \
    --scene ${2:-""} \
    --frame-stride ${4:-3}
```

## What to look for in the physics GIF vs state-injection GIF

| Observation | State-injection GIF | Physics GIF | Meaning |
|---|---|---|---|
| Drone inside pillar | Possible (old obs bug or p_des overshoot) | Impossible (physics prevents penetration) | Confirms bug vs real contact |
| Contact flash (red border) | Never shown | Shown when `ncon > 0` | Real physics event |
| Drone trajectory identical | Should match physics for no-contact episodes | Matches state-injection | Trajectory is clean |
| Drone deflects slightly off pillar | Not visible | Visible as brief lateral wobble | Real physics bounce |
| Attitude tilt at speed | Level (identity q until E4 U3 re-renders) | Correct tilt (live physics q) | Physics provides real attitude |

---

## Why this matters (digital twin rationale)

The physics GIF is the closest simulation to real hardware behaviour before actual
deployment. For the FM-PCC evaluation pipeline, it answers:

- "Does the drone actually contact the obstacle, or is it just the commanded trajectory overshooting?"
- "When DPCC fires at a near-miss, does the actual physics also have a near-miss, or is it safe?"
- "For pillar L_L_L episodes with the new U3 trajectory, does the physics confirm zero contact?"

The state-injection GIF answers "what trajectory did we command?". The physics GIF answers
"what did the drone actually experience?". Both are needed.
