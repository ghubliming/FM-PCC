## TL;DR — verdict (rev. 3 — separates "deviation" from "cause"; corrects rev-2 overclaim)

1. **No bug found in the eval / env / success / rollout / training-step / EMA / checkpoint save+load code.**
   Every link is logically equivalent to the upstream d3il reference that produces the paper's 0.278.
   In particular the checkpoint **save/load machinery** (`store_model_weights` / `load_pretrained_model` /
   `.pth` / EMA) is **d3il's, identical — not invented by us.**
2. **The success definition is correct and fully traced** (see §A). `done` and `success` are evaluated at
   the *same* env step (no one-step lag, no latching defect). Matches upstream byte-for-byte and the
   `D3IL_Metrics_…` doc's "binary, sticky (early-termination)" description.
3. **The one real divergence is checkpoint *selection criterion*, and it IS ours** — we keep best-**val-loss**;
   d3il keeps best-**simulation-success** (§B). **But existence of a deviation ≠ proof it caused the 0%.**
   Rev-2 called it a "sufficient cause" — that was an overclaim. It is the leading *hypothesis*, **not a
   verified cause.** Two live possibilities remain and we cannot yet tell them apart:
   (a) val-loss picked a bad checkpoint → d3il's success-selection would recover it (a deviation worth
   fixing); or (b) the model is genuinely ~0% **regardless** of selection → then d3il's own protocol would
   *also* give ~0% → **NOT our problem** (d3il/paper reproducibility).
4. **`0.278 / 0.139` is genuinely the image DDPM-ACT number** (paper Table 3), not a state/image mix-up:
   the same agent scores **0.849 / 0.749** from state (§C). So the target is the right row.
5. **"Is the paper lying?"** — **unfalsifiable from our run**, and the answer hinges on possibility (b)
   above. We did **not** replicate d3il's best-success selection, so we have no basis yet to call the number
   reproducible *or* inflated. If the decisive test (§ experiments) shows the model is ~0% under d3il's own
   protocol, the skepticism is warranted. Until then, reserve judgment.

> **Caveat the user is right about:** swapping to "use latest checkpoint" would prove **nothing** — "latest"
> is **not** d3il's method either (d3il selects best-*success*, not last-epoch). Trying an arbitrary third
> selection does not justify calling our original a "bug." The only legitimate test replicates d3il's
> actual protocol or runs d3il's own harness on our weights.

## §A. How success is REALLY defined — full trace (answer: correct, not the bug)

Reading the actual call chain (not just the env's `step`):

1. **Aligning `step`** (`aligning.py:288`):
   ```python
   observation, reward, done, _ = super().step(action)      # GymEnvWrapper.step
   self.success = self._check_early_termination()           # recompute proximity NOW
   return observation, reward, done, {'success': self.success, 'mode':…, 'mean_distance':…}
   ```
2. **`GymEnvWrapper.step`** (`gym_env_wrapper.py:90`) sets `done = self.is_finished()`, and
   **`is_finished()`** (`:124`) is:
   ```python
   return (self.terminated
           or self._check_early_termination()              # ← aligning override, sets self.terminated
           or self.env_step_counter >= self.max_steps_per_episode - 1)
   ```
3. **`_check_early_termination`** (`aligning.py:333`): `True` ⟺ `box_goal_pos_dist ≤ 0.018` **and**
   `box_goal_rot_dist ≤ 0.048`; on success it latches `self.terminated = True`.

**Consequence:** when the box first reaches the target, `super().step()` already returns `done=True`
(via `is_finished → _check_early_termination`), and the *very next line* recomputes
`self.success = _check_early_termination()` at the **same instant** (no action runs in between) ⇒
`success=True` on the terminating step. On timeout, `done=True` with `success=False`. So:

- **No one-step-lag bug** (my rev-1 worry was wrong — `_check_early_termination` runs *inside* `is_finished`
  during `super().step`, not only after).
- **"Sticky"** = the episode *ends* at first success, so it can't be un-recorded.
- Our custom eval reads `info['success']` from the **final** step (`eval_…py:169`), exactly like upstream
  `aligning_sim.py:119`. **MATCH.**

Thresholds (`pos_min_dist=0.018`, `rot_min_dist=0.048`, `robot_box_dist=0.051`) and the episode horizon
(`max_steps_per_episode=400`, the env default — upstream passes nothing and gets the same 400) are
**identical** between repos. So the success gate and the time budget are not the difference.

## §B. The selection deviation: ours, real — but causation UNPROVEN

**Is it ours or d3il's?** Unambiguously **ours**:
- d3il `run_vision.py`: every `eval_every_n_epochs`, run MuJoCo via `train_sim.test_agent(agent)` and keep
  the checkpoint with **best simulation success**.
- ours `train_d3il_visual_aligning.py:_train_vision`: keep the checkpoint with **best validation loss**, no
  MuJoCo. Our own docstring states the deviation explicitly: *"run_vision.py uses simulation success rate;
  we use val loss instead."*

The **training dynamics are identical** (`agent.train_vision_agent()` is the same call); only *which epoch's
weights* land in `eval_best_ddpm.pth` differs. d3il does **not** do val-loss selection anywhere — so this is
a deliberate deviation we introduced, not shared upstream behavior.

**Why it's a plausible cause:** validation denoising-MSE is well-documented to be **uncorrelated** with
rollout success for diffusion policies (that is *why* d3il selects on success). And the image task's peak
is only **0.278** (§C) — most checkpoints are worse, many ~0 — so selecting on the wrong signal *can*
plausibly land near 0%.

**Why it is NOT yet a proven cause (correcting rev-2):** "plausible" and "the only deviation" do not equal
"the cause." All of this is consistent with the *opposite* story too — that the trained model is genuinely
~0% from images under *any* selection (hard modality, our training amount/seeds, or an optimistic paper
number), in which case d3il's own best-success protocol would *also* report ~0% and **nothing here is our
problem.** The evidence on hand (weak-but-functional, ~0–0.86%) fits *both* stories. We cannot decide
between them by reading code — only by running the protocol-faithful test below.

Open unknowns (not separate bugs, just things we can't see without the run):
- *Which* checkpoint eval actually loaded — `eval_best_ddpm.pth` if present, else fallback `last_ddpm.pth`
  (`eval_…py:400-409`).
- Whether best-*success* would have appeared at all within 200 epochs (needs the training curve / a sim
  during/after training).

## §C. The paper number `0.278 / 0.139` — provenance & the "lying?" question

From `logs_in_develop/D3IL_Code_Guide/D3IL_Metrics_SuccessRate_Entropy_Explained.md §4F.4` (verbatim paper
Table 3, Image Data row):

| DDPM-ACT, Aligning | Success | Entropy |
|---|---|---|
| **State Data** | 0.849 ± 0.023 | 0.749 ± 0.041 |
| **Image Data** | **0.278 ± 0.071** | **0.139 ± 0.054** |

So `0.278` **is** the image number for exactly our agent (DDPM-ACT = `ddpm_encdec_vision`); it is not the
state number and not a different method. The image collapse is the modality (SE(2) pose from two 96×96
images), not a weak method.

**Could the paper be wrong/inflated?** Honest answer: **we cannot tell yet, and we don't need to.**
- It is plausibly transcribed correctly (image row, right agent, right task).
- It is low and high-variance (±0.071, ~26% relative); image-aligning runs are known to be noisy.
- We did **not** replicate the paper's best-success checkpoint selection — so we haven't actually run their
  protocol. Until we do (or run #1/#3 below), "the paper is lying" is **unfalsifiable from our data**, and
  our 0% is already fully explained by §B without invoking it.

**Bottom line for "does the code have a problem?":** **No logic bug found** — the eval, the
success/termination chain, the env, and the checkpoint save/load are all correct and match d3il. The only

d3il's own protocol would also show" (**not ours** — d3il/paper reproducibility). **A deviation is not a
bug, and swapping selection methods would not, by itself, justify calling it one.** Only experiment #1
