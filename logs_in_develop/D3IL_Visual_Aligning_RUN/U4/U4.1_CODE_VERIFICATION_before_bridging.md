# U4.1 — Code verification of the D3IL visual-aligning baseline run (pre-bridge audit)

**Date:** 2026-08-12 · **Epoch:** U4 · **Trigger:** the finished `seed_42` paper-scale run
(`ddpm_encdec_vision`, 60 ctx × 18 traj = 1080 rollouts) reports **success_rate 0.0** and the
results "feel terrible". Question asked before building anything on top of that data: *is the code
actually correct?*

**Verdict: no abort-level bug — proceed.** The eval rollout loop is faithful to upstream d3il, and
the U3 checkpoint-selection fix is in place and correct. One real bug was found (**B1: entropy is
hard-wired to 0.0**), but it cannot explain a zero success rate, and one **deviation** (F1) is the
leading remaining suspect for the terrible numbers. Parts U4.2 / U4.3 went ahead.

*Read-only audit. No behaviour was changed in this part; B1 is fixed in U4.3.*

## 2. B1 — REAL BUG: `entropy` has always been exactly 0.0

`eval_d3il_visual_aligning.py::compute_behavior_entropy` buckets rollouts with

```python
c = int(r.get('context', -1))
if not (0 <= c < n_contexts):
    continue                      # ← always taken
```

but the records built by `D3ILBaselineWrapper.update_rollout_info` carry
`success / steps / mean_distance / mode / context_info / ee_traj / dist_curve` — **no `context`
key**. Every rollout is skipped, `counts` stays all-zero, and
`-(0 · log(1e-12))` gives exactly `0.0`.

**Consequence:** `entropy` and therefore `score = 0.5·(success + entropy)` are meaningless in
*every* `results_seed_*.json` this script has ever written, including the six-seed U2 sweep. The
context index does exist one level down (`context_info.context_idx`), so nothing was lost — only
mis-read.

**Severity: moderate, not fatal.** Entropy is success-conditioned, so with `success_rate = 0.0` the
true entropy is 0.0 anyway; this run's headline number is unaffected. It would have silently
corrupted the diversity half of the paper comparison (`0.278 / 0.139`) the moment success became
non-zero.

**Fixed in U4.3** (record now carries `context`, plus a `context_info` fallback); the bridge (U4.2)
recomputes entropy for already-finished runs.

## 3. F1 — DEVIATION: only 10 single-rollout checkpoint probes

`_train_vision` is a faithful copy of `run_vision.py`, but the probe **cadence** is ours:

```bash
# Slurm_Codes/sbatch/d3il_visual_aligning_baseline/train_d3il_baseline.sh
EVAL_EVERY=$(( EPOCH / 10 ))     # 200 epochs → probe every 20 → 10 probes total
```

whereas the shipped config default is `eval_every_n_epochs: 2`. Combined with the upstream
selection rule, this is fragile:

* each probe is **one rollout on one context** (`train_simulation.n_contexts = 1`), i.e. a
  Bernoulli sample of a policy whose ceiling is 0.278;
* `best_success` starts at `-1`, so the **first** probe always saves, and later probes only
  overwrite on a strict improvement (`0.0 → 1.0`);
* ⇒ if no probe ever succeeds, `eval_best_ddpm.pth` is frozen at **epoch 20 of 200**, and if one
  does, it is the *first* lucky epoch, not the best one.

Upstream's own protocol shares the 1-rollout probe, but at 10× the cadence it gets ~100 chances
instead of 10. This is the leading remaining explanation for the run's numbers, and it is a
hyper-parameter choice of ours, not a code bug.

**Cheap decisive check on the cluster** (not run here — no cluster access from this container):

```bash
grep -c "New best success" <train log>     # 1 ⇒ the epoch-20 checkpoint was never beaten
grep "train_sim success" <train log>       # the 10 probe values
```

## 4. What the numbers themselves say

Decoded `d3il/environments/dataset/data/aligning/test_contexts.pkl` locally (60 contexts):

```
init  box→target xy distance:  mean 0.4465  std 0.0624   (min 0.3294, max 0.6067)
final box→target xy distance:  mean 0.4274  std 0.0802   ← results_seed_42.json
```

* Net progress over 400 steps: **~1.9 cm**, against a 1.8 cm success threshold — the box is
  essentially where it started.
* `n_steps_mean = 400.0`, `n_steps_std = 0.0` — **no** rollout ever early-terminated, i.e. no
  rollout ever satisfied the success gate.
* `mode_0_rate = 0.105`: `mode` in this env is *"was the EE within `robot_box_dist` of the box on
  the final step"*, so in ~90 % of rollouts the arm ended **away from the box**.

That profile is "policy barely engages the object", which is what an under-trained / badly-selected
checkpoint looks like (F1) — not what an obs/action-pipeline corruption looks like (that gives
exactly 0 with the box untouched *and* usually degenerate actions), and not what the U2 sweep's
"weak but functional" policy looked like.
