## 1. Bug B1 fixed — entropy is a real number again

`D3ILBaselineWrapper.update_rollout_info` now stores the context index on the record:

```python
'context': int(info.get('context', self.curr_context_info.get('context_idx', -1))),
```

and `compute_behavior_entropy` additionally falls back to `context_info.context_idx`, so it is
correct for any caller that builds records the old way. Before this, the lookup missed on every
rollout and `entropy` — hence `score` — was a hard 0.0 in every `results_seed_*.json` ever written
(U4.1 §2).

**This changes reported numbers.** Old JSONs keep their 0.0; new runs report the real value; the
bridge recomputes it for old runs. Any table mixing the three must say which is which.

---

## 2. Per-rollout timing is now a first-class number

The eval already measured `agent.predict()` wall time per step for the realtime logs, but threw it
away afterwards. Now `record_step(..., infer_ms=…)` accumulates it and each rollout records

```
avg_time = mean(step_times_ms) / 1000       # seconds per CONTROL STEP
```

which flows into three places: the npz (`avg_time`, per rollout), the legacy stats JSON (new
additive key `avg_inference_time_per_replan` — the exact name DA_VA_v2's flat-schema reader looks
for), and `results_seed_{s}.json` (`avg_time_mean` / `avg_time_std`).

**Semantics:** D3IL calls the policy on *every* step and serves the action chunk from the agent's
internal buffer, so this is per control step, not per replan like Gen14. Recorded in the npz as
`args.timing_semantics = 'seconds_per_control_step'`.

## 3. Native DA export

On by default; `--no-da-export` opts out, `--da-export-root NAME` renames the root
(config keys `da_export`, `da_export_root_name`).

```
logs/d3il_visual_aligning_baseline/DA_VA_d3il_baseline/          ← NO leading "_" = not legacy
    d3il_baseline_{agent}/{seed}/
        config_snapshot_d3il_baseline/snapshot_{ts}
        results[_train_set]/d3il_baseline/
            d3il_baseline.npz   unit_meta.json   diagnostics/rollout_{r}_stats.json
```

`results_train_set/` is used automatically under `--eval-on-train` (DA_VA_v2 records it as
`split=train`). Analysis:

```bash
python Data_Analysis/DA_VA_v2/main_da_batch.py \
    --parent-path logs/d3il_visual_aligning_baseline/DA_VA_d3il_baseline
```

**Additive and non-fatal.** The original outputs (results JSON, diagnostics, GIF/MP4/PNG/PKL,
realtime logs) are untouched; the export is wrapped so a failure prints a warning and never loses a
finished eval. It also re-derives `success_rate` / `entropy` through the shared module and warns if
they disagree with the eval's own summary — a self-check that the two paths cannot silently drift.

## 4. npz contents

Per-rollout `(N,)` unless noted: `n_success`, `success_strict`, `n_steps`, `avg_time`,
`mean_dist_per_rollout`, `mode_encoding` `(N,1)`, `context_index`, `context_box_init_xy` `(N,2)`,
`context_target_xy` `(N,2)`, `context_final_box_xy` `(N,2)`, `context_box_angle_deg`,
`context_target_angle_deg`, `context_init_xy_dist`, `context_final_xy_dist`,
`context_final_box_angle_deg`.

Scalars: `success_rate`, `entropy`, `score`, `n_rollouts`, `n_contexts`,
`n_trajectories_per_context`, `seed`, `complete`, plus the `args` object.

**Absent on purpose:** every `constraint_*` key, `success_relaxed`, and the heavy Gen14 traces
(`obs_all`, `sampled_trajectories_all`, …). No projector ⇒ no constraint metrics; no relaxed
success gate in the D3IL env; no planner ⇒ no sampled trajectories. Absent reads as NaN in
DA_VA_v2, which is the honest answer.
