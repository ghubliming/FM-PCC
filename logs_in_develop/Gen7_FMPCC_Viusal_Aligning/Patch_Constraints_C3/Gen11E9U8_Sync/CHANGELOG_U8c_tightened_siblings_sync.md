# Gen11E9U8c_Sync — `-tightened` siblings for geometry-keeping variants: **no visual-aligning edit needed**

**Date:** 2026-07-10. Companion to
`logs_in_develop/Gen11/Epoch9_PCC_Constraints/U_8_new_projection_var_upgrade/CHANGELOG_U8c_add_tightened_siblings_for_geometry_keeping_variants.md`
(the UAV-side origin) and follow-up to this folder's `CHANGELOG_U8b_geometry_alone_sync.md`.

## The UAV fix (recap)
On the UAV side, `config/uav_projection.yaml` **enumerates each `-tightened` variant explicitly**
in `projection_variants`. Two geometry-KEEPING new variants — `bounds_free` and
`model_free-bounds_free` — were added without their `-tightened` twins, even though
`model_free` (also geometry-keeping) had `model_free-tightened`. U8c added
`bounds_free-tightened` and `model_free-bounds_free-tightened` there. Rule:
**a `-tightened` sibling is meaningful iff the variant keeps geometry ON** (`enlarge_constraints`
shifts only geo_bounds/halfspace/obstacles); `geo_free*` variants correctly get none.

## Why visual-aligning (Gen7 FM + Gen6V4 diffuser) needs **no** change
The tightened dimension is implemented **differently** here — it is **orthogonal** to
`projection_variants`, not enumerated in it. The geo outer loop auto-generates the tightened twin
for **every** variant:

- `fm_visual_aligning_test/eval_fm_visual_aligning.py:2184-2190`
- `diffuser_visual_aligning_test/eval_visual_aligning_dpcc.py:2179-2185`

```python
_has_geo = any(t in _gc['constraint_types'] for t in ('geo_bounds', 'halfspace', 'obstacles'))
for _v in projection_variants:
    _run_items.append((_gs['name'], _gc, _v, False))          # nominal
if _enlarge is not None and _has_geo:
    for _v in projection_variants:
        _run_items.append((_gs['name'] + '-tightened', _gc, _v, True))   # tightened twin, EVERY variant
```

So `bounds_free` and `model_free-bounds_free` **already** produce a tightened run — as a
`<geo>-tightened` folder — for free. There is nothing missing to add.

**Adding `*-tightened` names to this yaml's `projection_variants` would be a bug**, not a sync:
each such name would then be run as a *base* variant under BOTH the nominal geo entry AND the
auto-generated `-tightened` geo entry → a double-tighten and a duplicate of the twin that
already exists.

The yaml already anticipates this asymmetry: `config/visual_aligning_eval.yaml:147-151` notes
that `geo_free`-family variants make their auto-generated `-tightened` twin a **harmless no-op**
(geometry already removed) — the exact same "tightened iff geometry kept" rule U8c states for
UAV, just enforced by the loop instead of by the list.

## Net effect
Both generations end in the **same** state — every geometry-keeping variant has a tightened
counterpart, `geo_free*` variants effectively don't — via two mechanisms:

| | tightened variants | who creates them |
|---|---|---|
| UAV (`uav_projection.yaml`) | listed explicitly | **the yaml** (U8c added the 2 missing) |
| visual-aligning (`visual_aligning_eval.yaml`) | auto-generated per variant | **the geo loop** (already covers all) |
